## Deliver a usable reference contribution

Supply concise user-facing text for your assigned section: supported syntax and
fields, types/defaults, precedence, prerequisites, output/exit behavior, side effects,
when changes take effect and known limitations. Include meaningful examples and
their applicable genuine execution evidence. Existing accurate material may be
reused; update only gaps/drift. Do not deliver only a source-code link or tell Docs
to discover the contract by running every command.

Coordinate the specific `docs/user/` section with Docs before editing. A draft
section in the normal component handoff is acceptable for editorial integration;
there should be one canonical final manual section. Verify against the identified
release and actual implementation; distinguish intended requirements, observed
behavior and defects. Explain JSON users may edit versus generated/immutable
payloads. Do not redefine product behavior to make documentation look consistent.

Reuse authenticated genuine receipts for existing operations, especially expensive
build/publication cases. This documentation assignment permits read-only inspection
and examples; fresh state-changing execution requires an already applicable issued
implementation/acceptance scope. No product repair, model build, production change
or synthetic test is commissioned here. Label unexecuted examples explicitly.

Deliver with the release identity, exact contributed section, evidence/limits and
any unresolved discrepancy. Docs receives the technical input on this same producer
record, edits it for coherence and follows examples under 10D/10E. You remain
accountable for technical corrections in your contribution; product defects go to
their owning implementation assignment. Future feature changes must include the
corresponding reference/example update, not silently leave the manual stale.
